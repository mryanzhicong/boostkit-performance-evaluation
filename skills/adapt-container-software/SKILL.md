# 容器化软件性能用例适配

本 Skill 遵循通用的 `SKILL.md` 目录形式，不依赖某家 agent 的专用工具或自动发现机制。使用者先定位**包含本文件的 Skill 目录**，下文以 `SKILL_DIR` 表示；完整目录必须连同 `references/`、`scripts/`、`assets/` 一起提供。复制、安装、权限和验收方式见[跨 agent 交接](references/deployment.md)。无法访问仓库、Shell、Docker 或目标 Runner 时，只完成可验证的层级，并如实报告，不声称生产验收通过。

本 Skill 的交付物是**能按 `build → start → test → stop` 分阶段运行、可独立运行、可核验结果**的软件用例，不是一份方案说明。默认要求：被测软件与测试工具在本次任务的私有容器内构建，正式 benchmark 也在**同一个容器**内运行。用户明确要求宿主机客户端等不同边界时，以用户要求为准，并在方案与 README 中写明差异。

开始前完整阅读仓库现行的 `doc/SOFTWARE_INTEGRATION.md`。`software/AI/lance/` 是“容器内构建＋容器内测试＋同一容器跨阶段复用”的主要代码及 README 结构参考：除 README 外，必须查看实际的容器创建、阶段复用与测试命令脚本，再用相同粒度写新用例。当前 `software/Others/unixbench/` 使用 KVM，不再作为 Docker 生命周期示例。`software/Database/redis/` 可参考服务就绪和多实例目录，但它当前在宿主机构建；涉及数据库部署、数据准备或客户端单独构建时，再参考 `software/Database/mysql/README.md` 的相应章节，其 Sysbench 在宿主机运行。**不可把参考案例的构建位置、CPU 限额或测试参数直接复制到新用例。**

## 先向用户确认适配类型

| 类型 | 何时选 | 默认改动范围 |
|---|---|---|
| 基础版（`base`） | 新接入上游原版，或更新已有基础用例 | 基础构建、生命周期、测试、解析和主 README；按需补注册、清单和入口。 |
| 调优版（`optimized`） | 为已有基础用例接入调优源码、补丁、插件或构建选项 | 同一软件目录的 `optimized.sh`、`README.optimized.md` 和主 README 链接；只补必要的分流或激活接线。 |

**用户必须明确本次做基础版还是调优版。** 若用户已明确要求「上游原版／开箱」或明确要求采用指定调优包、补丁或插件，无需重复问；若只给软件名、版本或参考指导，不能自行默认基础版，也不能从指导中出现的调优措施推断已获授权。可以先只读核实材料并给出建议，但必须问清楚「这次适配基础版（上游开箱），还是调优版？」；答复前不建分支、不改文件、不执行构建或测试。

调优任务若没有对应基础用例，先说明缺口，不用调优实现替代基础版。执行顺序：**确认类型与适配边界 → 建对应分支 → 按类型实施 → 共用验收**。工作流或独立入口的 `base` 默认值只用于运行已有用例，不用于决定新适配的类型。

## 调研与实施边界

### 1. 收到指导后先做边界调研（只读）

收到用户提供的文档、仓库、脚本或日志后，**先调研，不立即创建适配文件或改测试口径**。此阶段只读取资料、检查现有代码与目标环境、核对来源和约束；不要把指导文档中的命令当成可直接执行的实施指令。先明确用户本次要求的被测版本、上游原版/调优版、容器内构建与测试、单机或多机、资源限制、数据规模、正式场景、指标及是否授权完整长测；未明确的项目不能凭参考案例自行补全。

调研必须对照这些边界逐项给出证据和结论：

- 指导中的源码、测试工具、镜像、数据和命令是否真实存在、版本能否对应、x86_64/aarch64 是否均可获取与运行；私有地址与本机权限不能代替 Runner 可用性。
- 指导是否依赖专用补丁、优化开关、绑核、远程压力机、私有数据或特定硬件；逐项判断与“上游原版、开箱、单机、容器内构建测试”等本次边界是否冲突。
- 指导的完整阶段和实际参数是什么，现有 Framework、容器生命周期、结果契约能否承载；预估下载量、数据量、内存、磁盘和耗时，识别会造成长测后失败的依赖或结果缺口。
- 将每项做法标为“可直接沿用”“需做不改变测试口径的环境适配”“与边界冲突，需用户选择”或“尚无证据”；区分已核实事实、推断和未验证项。
- 阅读用户给出的原始测试文档、仓库或脚本，记录实际可执行的**版本、源代码/安装包、测试工具、数据集、正式命令、参数、输出字段**。文档中的优化补丁、CPU 绑定、系统配置、私有镜像或远程压力机不自动成为本次开箱测试要求。若“官方原版”和“必须打定制补丁才能运行工具”冲突，先说明冲突并取得选择，不擅自替换。
- 按[适配记录模板](assets/适配记录模板.md)形成适配记录：两个架构的来源和校验值、预计下载/数据/内存/运行时间、容器资源限制、网络或代理、离线数据目录、指标名与单位。可先在对话或临时草稿中填写；确认后的实际命令和口径进入软件 README。缺关键输入时先做可验证的部分，不能编造版本、校验值或结果。
- 把原指导中的每个**会影响结果的**步骤或参数逐项映射到本用例：原样采用、因开箱/单机等明确边界而排除、或暂未确认；记录实现位置与理由。不能只复制测试命令，却漏掉构建选项、数据准备、预热、采样次数、结果提取等口径。
- 在开工前核对两台目标 Runner **实际能访问**的本地包、私有仓库和数据。当前开发机有权限不等于 Runner 有权限；大数据集要先明确预置路径、体积、校验清单和缺失时的联网回退。固定负载与机器相关参数分开列出，并预先确认两架构输出能配对。

**先向用户给出简短的调研结论与拟采用口径**：哪些步骤沿用、哪些不采用及理由、关键风险和待确认事项。若存在版本/数据/测试方法冲突，或缺少会实质改变结果的选择，先停在调研阶段请求决定；不得悄悄替换上游、数据集、用例或指标。若边界清楚且用户已授权适配，报告调研结论后继续实施，无需为普通实施步骤反复等待批准。

调研结论须列出本次要改的文件，以及是否有操作越出容器。涉及下列例外时，在用户明确确认前不实施。调优任务还须列清调优差异与不变的基础测试口径。

#### 两种适配共用的容器边界

- **宿主机**只负责读取预置输入、准备任务目录、管理本次容器、框架解析与结果持久化和定点清理。宿主机装包、改 `sysctl`、大页、防火墙、系统证书或重启 Docker 等，必须作为单独的宿主预置，经确认后执行，不放进每轮用例。
- **容器权限**默认不启用 `--privileged`、Docker socket、宿主 PID/IPC 命名空间、额外能力或设备，不挂载整个可写宿主目录。确需例外，说明用途、最小权限和影响范围；容器内临时 root 不等于允许变更宿主机。
- **执行拓扑**默认同一容器完成构建和测试。宿主客户端、宿主机构建、多容器或子容器、远程压力机、KVM、额外绑核或资源限额不能从参考案例继承；确需时先确认各组件执行位置、资源、网络和端口、计时边界、清理责任及两架构可比性，再写入软件文档。
- **共享目录与异常回收**：预置输入默认只读；共享缓存写入须经确认，明确写入方、并发和半成品处理。不得覆盖预置包、数据或旧结果。强制取消后，只能定点回收能证明属于已结束任务的资源；不能按名称前缀扫删，清理失败须如实报告。

详细规则见[容器生命周期](references/container-lifecycle.md)。将本次例外及确认结果写入[适配记录](assets/适配记录模板.md)。

### 2. 核对任务和工作区，进入实施

- 查看 `git status --short --branch`、当前分支、`config/categories.yaml`、已有同类 `case.yaml` 和工作流的软件选项。保留用户已有改动。
- 调研关口通过、开始实施时，每次软件适配**必须**基于最新 `main` 新建分支：基础版用 `adapt-<software>-<version>`，为已有基础版接入调优用 `adapt-<software>-<version>-optimized`，其中 `<version>` 使用 `case.yaml` 中关联的被测版本，例如 `adapt-python-3.14.3-optimized`。不得直接在 `main` 或沿用其他适配分支。若工作区已有改动或目标分支已存在，先核对归属并保留现状，不能为建分支擅自覆盖、重置或丢弃用户内容。未经要求不提交、不推送，也不触发长时间的正式流水线。

## 按适配类型实施

### 基础版：交付完整开箱用例

以可信上游原版和开箱行为为准，不带入调优补丁、插件或非默认调优开关。接入所需且不改变被测行为的兼容处理要说明理由；改变被测行为、测试负载或指标必须先确认。

新用例要交付 `base.sh`、框架注册和 `case.yaml`、阶段脚本、解析器、独立入口和主 README；调优入口没有实现时留明确失败的占位。更新已有基础版时只改实际受影响的部分，不顺带实现或重写调优版。

### 调优版：只替换构建，保持基准不变

默认只改 `scripts/builders/optimized.sh`、`README.optimized.md` 和主 README 的入口链接。沿用已有软件注册、`case.yaml`、`base.sh`、测试命令、数据、指标和解析器。若缺少变体分流或跨阶段的调优配置接线，只补必要部分；确实需要改变基础构建或共用测试契约时，先说明原因并取得确认。具体实施见下文[调优构建](#调优构建)。

## 共用实施与验收

### 3. 先确定执行边界和目录

在修改代码前画出本用例的实际调用链，按下面的默认形态实现：

```text
Framework prepare
  → build：准备镜像 → 创建本次容器 → 容器内安装依赖、获取/校验源码、构建软件与测试工具
  → start：找到 build 创建的容器 → 校验产物／启动容器内服务 → 有界等待就绪
  → test：找到同一容器 → 容器内执行正式测试 → 保存完整原始输出 → 解析指标
  → stop（成功、失败、可处理的取消均应调用）：先保存诊断日志 → 停服务 → 仅删除本任务容器
  → Framework finalize → 全局清理工作目录 → 将未清理的 RESULTS_DIR 持久化 → 独立上传工作流
```

Framework 的每个阶段是**新 Shell**；容器、文件、PID 和端口必须能由 `PERF_RUN_ID` 等变量重新定位，不能只存在于 `build` 阶段的 Shell 变量中。`start` 和 `test` 只复用容器，不重新 `docker run`、`docker load`、下载镜像或重新编译。例外必须记录原因并测试实际工作流路径。

在调用链中同时标出**谁写入、谁清理**每个 bind mount：容器内构建器（如 Bazel）的产物即使位于私有目录，也必须能由宿主 Runner 读取和删除。不能以“容器内构建成功”代替权限和全局清理验收。

### 4. 建立或核对文件和清单

新用例在 `software/<分类>/<软件>/` 建立 `README.md`、`case.yaml`、`<软件>_test.sh`，以及 `scripts/common.sh`、`scripts/builders/{base,dispatch,optimized}.sh`、`scripts/stages/{start,test,stop}.sh`、`scripts/results/`。按实际分类注册到 `config/categories.yaml`；如工作流用显式软件下拉列表，更新要开放的软件选项。已有用例按上述类型范围变更，其余只核对。`case.yaml` 的 `name/category/versions` 必须与目录和实际产物一致，四个阶段必须指向真实存在的函数。具体字段、路径和指标映射见[框架与结果契约](references/framework-and-results.md)。

逐项核对：清单的每个脚本/函数/输出路径确实存在，`required` 输出在所声明阶段产生，软件选项能从**目标工作流**选到，独立入口与 Framework 调用相同实现。不能只让目录结构“看起来齐全”。

`common.sh` 接收 Framework 传入的 `SOFTWARE_VERSION`、`EXPECTED_ARCH`、`PERF_RUN_ID`、`PERF_WORK_DIR`、`RESULTS_DIR`、`PERF_ACTUAL_VERSION_FILE` 和工作流选择的 `PERF_VARIANT`。独立运行才生成默认值。源码、二进制、数据、临时文件、服务 socket/PID 放在 `PERF_WORK_DIR`；清单声明的原始日志和 JSON 放在 `RESULTS_DIR`。容器内挂载**相同绝对路径**。两个目录职责不能混淆。

### 5. 实现 `build`：在容器内完整构建

按[容器生命周期](references/container-lifecycle.md)逐项实现：检查 Docker daemon；优先取本地离线官方镜像并核对 SHA-256、架构和系统版本；镜像缺失才下载；以包含软件、架构、run ID 的名称和归属 label 创建**一个**私有容器。已有同名容器时拒绝覆盖。`--network=host`、UID/GID、挂载、资源限制、代理与 CA 都按本用例实际需要明确设置，不假设它们会自动继承。

在该容器内安装依赖，获取并校验本地优先的源码/安装包；如需网络，使用已核实的上游地址。**构建命令通过 `docker exec` 在容器内执行**，不能只把宿主机编译好的产物挂进去。构建结束前核验编译期头文件/工具、运行期动态库及正式测试会用到的 Python/Go/Rust 等依赖；不能等耗时测试开始才发现缺模块。源码归档或缓存只有校验通过才算命中，半成品不能复用；细则见[容器生命周期](references/container-lifecycle.md)。构建完成后在容器内运行版本命令，将实际版本写入 `PERF_ACTUAL_VERSION_FILE`；不能把请求版本原样伪装成实际版本。`dispatch.sh` 只选择一个完整的 `base` 或 `optimized` 构建；调优版未实现时明确失败，不回退基础版，也不写成功的 `build_variant.json`。

创建容器时优先用 Runner 的 UID/GID 执行普通构建和测试，并把 `HOME` 及工具缓存、临时输出指向本次任务的可写挂载目录；逐条检查 `docker exec` 是否覆盖了用户或 HOME。仅需特权的安装、改源、证书步骤临时以 root 执行，不得让 Bazel 等构建器在挂载目录生成 Runner 无法删除的 root 文件。确需 root 构建时，限定写入目录，并在退出前将本任务产物所有权交还 Runner；失败路径也必须执行该收口，不能对共享目录做递归改属主。

#### 调优构建

以 `software/Toolchain/python/` 为**分流接线**参考：读 `case.yaml`、`scripts/builders/dispatch.sh`、`scripts/builders/optimized.sh` 和 `python_test.sh`。Python 当前的调优函数是**明确失败的占位**，不能当作已实现的调优例子；也不要照搬其宿主机构建方式。容器生命周期以 Lance 和本 Skill 的要求为参考。

1. **先确认调优输入。** 记录要测试的基础版本、调优源码提交、补丁顺序及校验值、插件或替换依赖版本、开启方式、适用架构与各架构的实际差异。核实这些输入在目标 Runner 可获得。如果指导要求改测试命令、数据或指标，先说明与“只调整 build”的冲突并确认新口径，不能擅改基础版测试。

   Runner 预置的调优源码包、插件和专用依赖包直接放在 `/home/runner/software/<software>/optimized/`（Python 即 `/home/runner/software/python/optimized/`），**不再按版本或架构分子目录**。用实际包名区分版本和架构，按明确的文件名和校验值选包；共享预置目录不作为构建或安装输出目录。
2. **在同一软件目录增加完整构建入口。** 只保留一份 `case.yaml` 和一条软件注册。其 `build` 固定指向 `scripts/builders/dispatch.sh` 的入口，按 `PERF_VARIANT` 调 `base.sh` 或 `optimized.sh`，默认 `base`；独立入口的 `--variant` 使用同一分流。调优构建须能在干净的任务容器中独立完成依赖准备、取源码、应用补丁或装插件、配置、编译、安装及验证。可复用通用函数，不先运行整个基础版构建，不依赖基础版残留产物；补丁只作用于本任务的私有源码副本。
3. **复用测试，验证实际生效。** 调优构建向原 `start/test/stop` 提供同样的路径、二进制或解释器接口，复用原测试工具、命令、参数、解析器和指标契约。需要激活插件或加载调优库时，由调优构建准备任务私有的运行配置，并用实际版本、已加载模块/动态库或功能探针验证生效；不能只检查编译成功或文件存在。基础版不得继承调优补丁、插件、环境变量或可写构建目录。缺少调优输入、不支持当前架构或验证失败都返回非零，不回退到基础版；全部构建检查通过后再写 `build_variant.json`，保留实际调优来源及验证证据。
4. **保持两个变体隔离。** 复用工作流的 `base/optimized` 下拉列表，默认 `base`，仅调优任务标题加 `optimized`。持久结果沿用现有路径：基础版在版本目录下，调优版在版本目录的 `optimized/` 下；独立运行也使用不同结果目录。调优报告比较 **x86_64 optimized 与 aarch64 optimized**，不生成同架构的前后对照，不更新基础版 baseline。验证默认基础路径仍能跑、显式调优命中正确产物、混合变体不会被配对。
5. **单独写调优文档。** 在该软件主 `README.md` 同级新增 `README.optimized.md`，由主 README 链接过去。调优文档写明预置包名称、来源和校验值、适用架构、容器内完整构建与安装命令、启用及生效检查、`--variant optimized` 的运行方法；共用的测试命令、数据和指标留在主 README，调优文档引用即可。调优构建仍为占位时，不把它写成可用流程。

### 6. 实现 `start`、`test`、`stop`

- `start`：重新计算容器名，检查容器正在运行且 label 属于本任务；无服务软件验证 benchmark 可执行和数据就绪，服务型软件在**同一容器内**启动进程，使用任务独占端口/数据目录，并通过真实 socket、端口或 API 有界检查就绪。不能仅 `sleep` 后认定成功。
- `test`：再次检查同一容器；先确认服务/任务健康、数据集及全部正式测试依赖，再按已确认的命令在容器内运行。保存**完整** stdout/stderr 和工具原生文件，`tee` 管道必须保留 benchmark 原退出码。预热与正式测试分清；只解析正式测试。测试参数、数据集校验值和实际并发写入结果。若测试工具报失败、缺场景、数值不可能或结果解析失败，返回非零，不生成“成功”报告。长测要有进度和有界等待，但不能仅为避免超时擅自缩小数据量、线程或轮次。
- 正式测试矩阵先列出**预期场景集合与数量**（数据集、线程/副本、模式、轮次等），再以实际原始输出逐项核对；允许用户指定只测子集，但报告必须如实标出该子集。任何静默跳过、工具内部失败、场景数不足都不能作为完整成功。
- `stop`：在容器仍存在时将容器／软件日志复制到 `RESULTS_DIR`；停本任务服务；核对容器 label，再停／删本任务容器。容器尚未创建、已经不存在或重复调用时要安全收口。不能 `docker prune`、扫删其他任务容器、删除共享离线目录或在 `stop` 里清空 `RESULTS_DIR`。

如果有多实例需求，先把实例编号用于容器名、端口、数据目录、socket、日志和清理标签；默认实例数及报告如何聚合必须明说。不要把单实例脚本隐式循环成多实例。更多可直接执行的容器检查点和命令形态见[容器生命周期](references/container-lifecycle.md)。

### 7. 实现解析、独立入口和 README

解析器必须从保存的正式原始输出逐项提取数值，校验必需项齐全、唯一、数值有限、单位和方向正确；动态场景需保留场景身份，不凭样例猜测输出字段或丢掉实际指标。跨架构固定负载写 `parameters`，机器相关事实放运行上下文或指标身份；不能把不同线程数或不同数据集强配成一项。`case.yaml` 的 `outputs`、`metrics.source`、`metrics.collection/definitions` 必须与真实 JSON 一致。**正式长测前**用真实或保真的双架构样例运行解析和汇总，发现 `resolved workload parameters differ` 时先修正字段归属，不能事后硬配。

从实际工具输出做一次**指标盘点**：每个正式场景可供报告的字段，分别标记“纳入指标”“仅保留原始数据”“排除及原因”；再核对 JSON、`case.yaml` 和最终 Markdown 中的场景身份、单位、方向与分组。不能只验证已写出的指标而不知道漏了什么。

独立入口接受 `--version`、`--variant`、`--results-dir`，调用**同一套**阶段函数；失败或中断也执行 `stop`，并只清理由本次独立运行创建的私有工作目录。README 以 `software/AI/lance/README.md` 为容器用例结构参考，涉及数据库部署、数据准备或客户端单独构建时再参考 `software/Database/mysql/README.md` 的相应章节；不要求所有软件照搬其数据库流程。

README 必须让读者**不打开脚本也能复现测试流程**，且每个命令块与实际脚本逐项一致：写明实际来源和离线优先级；完整的容器创建命令（镜像、名称、网络、用户、挂载、资源限制、代理/证书条件）及创建阶段；容器内依赖、源码获取与构建命令；`start` 的实际服务启动及就绪条件；`test` 的完整 benchmark 命令、数据路径、预热/正式轮次、并发/时长/场景及原始输出；`stop` 的本任务清理边界；指标从哪些原始字段提取、单位/方向/分组、产物路径和独立运行命令。若命令由变量拼装，先给变量的实际来源和取值规则；条件分支分别说明，不能用 `...`、`按需配置`、`运行官方测试`、`容器内执行` 代替关键选项。与用户原指导有差异时列出原命令/参数、实际命令/参数及理由；没有证据的内容标为未验证，不写成已完成。

### 8. 分层验证后交付

基础版验收完整生命周期和结果契约；调优版还要核对基础版不受影响、调优确实生效、结果分开且只同变体配对。未改动的共用阶段做回归验证，不为通过验收而重写。

本机适配验证（实际构建、启动、短负载测试、独立入口及失败路径演练）必须在 `/tmp` 下为本次测试创建私有目录，将工作目录、结果目录和容器写入用的 bind mount 指向该目录；不得在仓库目录内运行这些测试或留下构建、数据与 benchmark 产物。`pytest`、静态检查等需要从仓库目录执行的常规代码测试除外，其临时产物仍应使用临时目录。具体命令形态见[验证清单](references/verification.md)。

按[验证清单](references/verification.md)执行，并用[适配记录模板](assets/适配记录模板.md)逐项登记完成状态与证据：先从实际 `SKILL_DIR` 调用 `scripts/check_adapter.py` 并运行 `framework/catalog.py validate` 检查接线；再验证解析器、失败路径和独立入口；然后在可用 Runner 上做容器内构建与短用例烟测；只有需要正式性能数字时才跑完整矩阵。**静态检查通过 ≠ 容器构建通过 ≠ 双架构正式测试通过。**

交付门槛是“所有适用项有实现或明确的未完成状态”，而不是“某个命令退出 0”。交付前对照实际 `docker run`/`docker exec`、构建/测试脚本、`case.yaml` 和用户原指导逐项复核 README；容器启动或正式测试命令被一笔带过、关键参数未写、文档与脚本不一致，都视为未完成。每项标记已验证、未验证、阻塞或不适用，并给出位置/命令/产物；未验证或阻塞项必须在交付中显式说明，不能笼统宣称完整通过。对用户限定不跑的正式矩阵，只完成其授权范围，保留未跑项状态。

权限验收必须覆盖一次真实的容器写入：核对容器内 `id`、`HOME`、实际构建输出及缓存目录的 UID/GID，再以宿主 Runner 身份读取并清理**本次 `/tmp` 烟测目录**。不得只在 root Shell 下执行清理，也不得把 `find: Permission denied` 当作全局清理脚本自身的问题。未能以 Runner 身份完成清理时，容器生命周期仍未验收通过。

交付时写出：实际修改文件、分支、哪些命令在什么环境真实执行、观察到的产物和容器清理结果、未测环节、预计正式耗时。任何下载、构建、测试或上传问题都要定位到具体阶段；上传失败不应让已持久化的正式测试结果被误删或要求无谓重跑。
